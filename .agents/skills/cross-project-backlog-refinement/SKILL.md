# 승인 후보 선정·정제와 작업 연결

`jira` provider는 공통 목표·원본·중복 검토와 `docs/jira-workflow.md`의 승인 확인·정제·관계 절차를 따른다. 아래 Draft 전환·GitHub 공식 Sub-issue·Project 초기 반영 지시는 `github_projects`에만 적용한다. Jira 구현 Task의 착수 가능 전환은 사용자가 직접 한다.

공통 운영 루트의 `AGENTS.md`에 따라 프로젝트를 식별하고 대상 루트의 `ai-dlc.yaml`을 확인한다. 절차는 공통 루트의 `docs/workflow.md`를 따른다. 프로젝트 설정과 기록은 대상 루트 기준이다. 서비스·저장소 역할·선택 provider의 상태·라벨은 설정으로 해석하며 특정 서비스를 하드코딩하지 않는다. 정제 요청은 승인 후보 선정과 필요한 구현 작업 정제·연결을 포함한다. 정상 범위의 작업에 추가 실행 승인을 반복 요청하지 않는다. 사용자가 분석·계획만 요청하거나 범위를 제한하면 그 지시를 따른다.

`백로그 정제해` 요청에서 후보가 없으면 선택 provider의 후보 전체를 조회하고 실제 승인된 후보를 탐색한다. 지정 후보가 있으면 지정 순서를 우선한다. 사용자·다른 경로의 후보도 승인 원본을 확인해 처리하며 feature-discovery 실행은 요구하지 않는다.

## 최대 2개 선정

workflow의 정제 후보 자동 선정 기준을 적용한다. 한 요청의 지정·자동 후보와 부분 성공 재개를 합쳐 최대 2개다. 특정 후보만 요청한 범위를 넘기지 않으며 유효 후보가 적으면 수를 채우지 않는다.

- 열린/닫힌 GitHub Issue·PR과 선택 provider의 후보·전환 이력으로 중복을 확인한다. Draft 조회는 `github_projects`에서만 수행한다. 이미 정제·구현된 기능은 새 작업 대신 기존 작업을 보고하고 재사용한다.
- 목표 불명확·승인 확인 불가·우선순위 충돌·의존성 불명/순환은 보류한다. 세부 결정만 남은 후보는 질문·결정 라벨·Backlog로 정제할 수 있으나 Ready로 처리하지 않는다.
- `github_projects`는 Draft의 Project Priority를 설정으로 해석하고 선행 관계를 고려한 뒤 high→medium→low→미설정 순으로 검토한다. Jira는 `jira.priority_order`와 `jira-workflow.md`를 따른다. 동률은 생성 시각 오래된 순→안정적인 후보 ID 순이다. 실제 작업의 선행 조건도 확인한다.
- 선행 구현 미완료가 정제 자체를 막는 것은 아니다. 범위가 명확하면 의존 관계와 Backlog를 유지하며 구현 착수와 구분한다.
- 지정 후보부터 검토하고 남는 자리는 자동 선정한다. 지정 후보의 미승인·보류, 자동 후보의 선정·제외 근거와 조회 한계를 보고한다.

## 정제와 연결

UI가 관련된 후보는 공식 UI 명세의 화면·경로·사용자 동작·공통 상태 처리를 참조해 구현 범위와 완료 조건을 정리한다. API·인증·데이터 구조는 기존 공식 명세를 따르고 미결정 UX는 Parent의 결정 질문으로 남긴다.

선정 후보의 목적·범위·제외 범위·계약 참조·완료 조건을 정리하고 필요한 구현 역할에만 작업을 나눈다. 미연결 역할이 필요하면 그 부분을 보류하며 불필요하다고 간주하지 않는다. 각 구현안은 대상 저장소 템플릿과 독립 실행 요건을 따른다.

`requirements`의 공식 요구사항과 `contracts`의 API·인증·ERD·UI를 설정된 역할의 기본 브랜치·경로에서 조회하고 workflow에 따라 URL·SHA를 확인한다. Parent와 구현 작업은 관련 원본을 참조하고 기능별 범위·완료 조건·결정을 작성한다. 세부 명세를 복제하거나 Backend 사본을 공식 원본으로 대체하지 않는다. 원본 조회 실패·Parent나 구현과의 불일치는 해당 범위를 보류하고 중요한 요구사항·계약·인증·DB 결정은 사용자에게 남긴다.

`github_projects`에서는 Parent를 `backlog.parent_repository_role` 저장소에, Sub-issue를 필요한 구현 저장소에 두고 공식 GitHub Sub-issue 관계를 사용한다. URL만으로 대체하지 않는다. `jira`에서는 `jira-workflow.md`에 따라 단일 구현이면 후보를 같은 키의 Task로 유지하고, 여러 구현의 통합 완료 판단이 필요할 때만 기존 후보를 같은 키의 Epic으로 전환해 필요한 Task를 연결한다. 전환 불가 시 별도 Epic으로 우회하지 않는다. 같은 관계는 재추가하지 않고 다른 Parent로 자동 교체하지 않는다.

`github_projects`에서는 후보 승인·중복 재확인→Draft 전환→필요 Issue 생성/재사용→공식 연결→양방향 조회→Project 확인을 수행한다. `jira`에서는 같은 키 재사용·필요 시 Epic 전환과 Jira 관계 조회를 수행한다. 부분 성공은 기록하고 기존 작업·관계를 재사용해 남은 단계만 재개한다.

신규 아이디어 발굴·Draft 등록·승인 변경은 하지 않는다. 선정·보류·중복 근거, 실제 Parent/구현 Issue와 미실행 본문안, 식별자·Link Key, 관계·우선순위·의존성·미결정·통합 검증 기준을 보고하고 종료한다. 다른 Skill이나 개발 사이클을 자동 시작하지 않는다.

정식 Issue의 사용자 협의 기반 상세화와 착수 승인은 별도 요청의 `issue-refinement`가 담당한다. 이 Skill의 초기 정리와 Issue 생성은 상세화 완료나 개발 착수 승인이 아니다.
