# 공통 기능 아이디어 발굴

루트의 `AGENTS.md`, `ai-dlc.yaml`, `docs/workflow.md`를 읽는다. 경로 기준은 저장소 루트다. 서비스 선택과 Project·필드·계약·저장소는 설정에서 해석하며 특정 서비스 정보를 하드코딩하지 않는다.

사용자가 아이디어 제안해 또는 기능 아이디어 발굴·제안을 요청하면 독립 실행한다. 다른 Skill 실행 기록은 필수가 아니다. 이 요청은 중복·권한 확인을 통과한 후보 최대 3개의 Pending Draft 등록과 Project 필드 반영을 포함하며 후보마다 추가 승인을 요구하지 않는다. Draft 등록은 후보 승인·정제·Parent/Sub-issue 생성·개발을 자동 시작하지 않는다.

## 검토와 제안

- UI 명세의 화면·경로·사용자 동작과 기존 구현을 비교해 후보의 필요성·차이를 확인한다. 명세의 후속 기능 목록만으로 승인이나 구현 완료를 추정하지 않는다.
- Project 비전, `requirements`의 공식 요구사항과 `contracts`의 API·인증·ERD·UI, 기존 Parent와 각 구현 역할의 기능을 확인한다. 원본 역할의 기본 브랜치·경로를 설정에서 해석하고 workflow에 따라 URL·SHA를 확인한다. 단일 저장소의 내부 개선만으로 한정하지 않고 전체 사용자 흐름·프로젝트 목적·실현 가능성을 검토한다.
- Backend의 기존 명세를 공식 원본으로 대체하지 않는다. 원본 조회 실패·Parent나 구현과의 불일치는 확인 범위와 보류 사항으로 보고하며 중요한 요구사항·계약·DB 결정을 임의 확정하지 않는다.
- 열린/닫힌 Issue·PR, 기존 Draft·전환 이력을 끝까지 조회해 중복·방향 충돌을 확인한다. 미연결 저장소나 조회 실패가 있으면 영향과 확인 범위를 명시하며 중복 없음으로 단정하지 않는다.
- 필요한 근거를 확보한 유효 후보만 최대 3개 선택한다. 후보가 없으면 생성하지 않으며 수를 채우기 위한 제안을 하지 않는다. 필수 자료 부족으로 등록 가능성을 판단할 수 없으면 외부 등록은 보류하고 분석 한계를 보고한다.
- 제목, 배경·제안 내용·예상 효과, 기존 작업과의 차이, 미결정 사항과 고유 Candidate ID를 포함한다. ID는 기존 후보·전환 Issue와 비교하고 같은 후보의 재개 중에는 바꾸지 않는다.
- 필드는 설정된 AI 제안자와 Pending 매핑을 사용하고 개발 Status는 비운다. 초기 Pending 설정 외에 승인 상태·Project 비전을 변경하지 않는다.

## 등록과 종료

사용자의 기능 아이디어 발굴·제안 요청에 따라 설정된 Project에 최대 3개 Pending Draft를 등록한다. workflow의 제안·식별자·부분 실패 절차를 적용하며 중요한 정책이나 후보 승인 상태를 임의 변경하지 않는다. 등록 제외 지시가 있으면 제안만 한다. 등록 직전 중복을 재확인하고 Candidate ID를 본문에 포함한다. 필드·개발 상태와 생성 결과를 재조회하며 실패·결과 불명 시 해당 등록 흐름을 중단한다.

재시도 전 후보 ID로 기존 Draft·전환 Issue를 조회하고 중복 여부 확인 전 재생성하지 않는다. 같은 요청을 재개할 때 이미 등록한 후보도 최대 3개에 포함한다.

후보별 제목·ID·본문안 또는 실제 링크, 제안 근거·예상 효과, 중복 확인 범위·미결정·미검증과 등록하지 않은 이유를 보고하고 종료한다. `cross-project-backlog-refinement`나 개발 사이클을 자동 호출하지 않는다.
