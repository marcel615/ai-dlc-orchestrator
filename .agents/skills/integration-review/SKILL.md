# 요청 기반 변경 영향 검토

루트의 `AGENTS.md`, `ai-dlc.yaml`, `docs/workflow.md`를 읽고 완료 근거 확인에는 `docs/integration-checklist.md`를 적용한다. 경로 기준은 저장소 루트다. 서비스·저장소·계약·Project·상태 파일 위치는 설정으로 해석한다. 영향 검토 요청은 조회·분석·로컬 상태 갱신·후속 작업 제안까지 수행하며 실제 Issue·Draft·관계·Project·코멘트·서비스 PR은 변경하지 않는다.

## 대상 탐색과 중복 분석 방지

특정 PR을 지정하면 그 PR을 우선 검토한다. `변경 영향 검토해`처럼 지정이 없으면 활성·연결된 저장소 역할 전체의 신규·갱신 PR을 자동 탐색한다. 공통 관리 저장소도 포함하고 같은 저장소는 한 번 조회한다. 비활성·미연결 역할의 공백을 보고한다. 선행 기능 제안·정제 기록은 필요하지 않으며 상시 감시 서버·주기 작업을 만들지 않는다.

workflow의 요청 시 PR 탐색과 이력 절차를 적용한다.

- `review.state_file`의 단일 JSON에서 서비스별 저장소 완료 시점과 PR별 최신 분석 상태를 읽는다. 검증 보고서를 만들거나 검색하지 않는다. 상태가 없으면 빈 상태로 시작하고, 손상·조회 실패는 완료로 추정하지 않는다.
- 요청 시작 UTC를 상한, 저장소별 마지막 조회 완료 시각을 하한으로 삼아 경계를 포함해 조회한다. 첫 이력이 없으면 사용자 지정 범위가 없는 한 전체 PR 이력을 확인한다. open·closed·merged를 포함하고 페이지 누락·조회 중 변동을 확인한다.
- PR URL·base/head SHA·상태, 관련 공식 요구사항·계약의 저장소·경로·SHA·소비자 기준 SHA·PR 본문·관련 코멘트·사용자 결정 버전이 같고 분석 완료인 경우만 상세 분석을 재사용한다. updatedAt만으로 재사용하지 않는다. 원본 위치·내용 등 맥락 변경이나 보류·실패 건은 목록 갱신 여부와 별도로 재검토한다. 이전 분석에서 현재 설정과 다른 공식 원본을 사용했으면 설정된 공식 원본을 기준으로 재검토한다.
- workflow의 상태 형식에 따라 해당 PR의 base/head·상태·원본 갱신 시각·관련 맥락·판정·complete/deferred·검토 UTC를 같은 JSON에 갱신한다. 다른 PR·서비스 상태는 보존한다. 전체 조회·필수 분석이 끝난 저장소만 완료 시점을 전진시키며 단일 PR 검토·실패·보류로 전체 완료를 표시하지 않는다.
- 상태를 확보·저장하지 못하면 중복 생략의 한계를 최종 응답이나 승인된 PR 본문에 보고한다. 상태 교체 실패 시 이전 파일을 보존하며 실행마다 새 보고서·상태 사본을 생성하지 않는다.

## 영향 분석

UI 명세와 화면·라우팅·사용자 동작·공통 상태 처리의 변경이 API 소비·인증 흐름·완료 조건에 미치는 영향을 확인한다. 관련 UI 원본의 저장소·경로·SHA도 분석 맥락에 포함하고 UI 기준 추가·변경이나 이전 분석의 관련 기준 누락 시 재검토한다. Frontend의 기존 문서·코드는 구현 비교 자료이며 공식 UI 원본을 대체하지 않는다.

`requirements`의 공식 요구사항과 `contracts`의 API·인증·ERD·UI를 설정된 역할의 기본 브랜치·경로에서 조회하고 workflow에 따라 URL·SHA를 확인한다. 원본 조회 실패 시 다른 저장소의 명세 사본으로 대체하지 않는다. Parent는 기능별 범위·완료 조건·결정 이력으로 대조하고 공식 원본과의 충돌은 보고한다.

대상 base/head와 전체 변경 파일에서 요구사항·계약·ERD·UI·화면·라우팅·엔티티·마이그레이션·DTO·컨트롤러·인증·관련 테스트 diff를 확인하고 patch 누락은 원문으로 보완한다. 명세 저장소 PR은 문서의 base/head, 구현 PR은 현재 공식 원본과 구현 diff를 대조한다. 설정된 공식 원본이 아닌 구현 저장소의 기존 명세는 구현 비교·과거 이력 자료로만 사용하며 해당 문서 변경만으로 공식 계약 변경을 판정하지 않는다. 존재하지 않는 OpenAPI를 원본으로 취급하지 않는다. 중요한 요구사항·계약·인증·DB 결정은 사용자에게 남긴다.

영향 없음·호환 영향·비호환 영향·보류를 항목별로 분류한다. 서버 차이·소비자 사용·연계 작업 필요성을 구분하고 영향 없는 변경도 근거와 버전을 기록한다. 미연결 소비자를 영향 없음으로 판단하지 않는다.

기존 Issue·후보·공식 관계를 확인해 기존 작업 재사용 또는 필수 연계 작업안을 제시한다. 공통 기능의 작업은 기존 Parent의 공식 Sub-issue로 계획하며 URL은 대체 수단이 아니다. 관계 중복·다른 Parent 충돌·부분 실패는 workflow를 따른다.

선택 기능은 별도 검토 사항으로 보고한다. 기능 후보 등록은 `feature-discovery`, Approved 후보 정제·생성·연결은 `cross-project-backlog-refinement`의 책임이다. 다른 Skill이나 개발을 자동 시작하지 않는다.

비호환 변경의 사용자 결정·소비자 대응·호환 기간·배포 순서·복구 제약을 제시한다. 실제 Merge·종료 사유·대상 head CI·계약·통합 증거를 구분하며 Merge 차단이나 실행하지 않은 검증의 성공을 보장하지 않는다.

대상·판정·근거, 재사용한 분석·새 분석·영향 없음·보류, 조회 완료 범위, 필요한 후속 작업과 재개 조건을 최종 응답이나 승인된 PR 본문에 보고하고 종료한다. 별도 Markdown 검증 파일은 만들지 않는다. 후속 작업 등록이나 후보 정제는 별도 작업 요청의 해당 Skill에서 수행하며 이 검토가 자동 실행하지 않는다.
