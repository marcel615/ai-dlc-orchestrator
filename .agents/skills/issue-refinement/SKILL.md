# 사용자 협의 기반 Issue 상세화

공통 루트 `AGENTS.md`, `docs/workflow.md`, `docs/integration-checklist.md`와 대상 로컬 지시를 따른다. 선행 Skill 실행은 필요하지 않다. 사용자가 지정한 정식 Issue의 Parent와 공식 Sub-issue 관계를 양방향 조회하고 관련 작업 범위를 확인한다. Sub-issue가 지정되면 해당 작업과 Parent·영향받는 형제만 다루고, Parent가 지정되면 필요한 자식을 검토한다. 다른 Parent로 재배치하지 않는다. 대상이나 공식 관계를 확인할 수 없으면 해당 범위를 보류한다.

최초 상세화와 사용자가 요청한 선택적 재상세화를 같은 절차로 수행한다. 계약 변경 후라면 변경 Issue·PR의 실제 상태와 Merge된 공식 원본을 확인하고 이전 Issue의 기준 SHA와 차이를 비교한다. 미병합 PR이나 제안은 예정 사항으로 구분하고 최신 공식 계약으로 표시하지 않는다. 관련 없는 Issue를 일괄 수정하거나 구현을 시작하지 않는다.

## 분석과 협의

기존 Issue 본문·결정·의존성·Project 상태·관련 PR과 사용자 결정 출처를 확인하고, `requirements`와 관련 `contracts`의 설정된 기본 브랜치 원본을 URL·commit SHA로 조회한다. 목표·범위·제외·사용자 흐름·오류와 경계 조건·역할별 책임·의존성·수용 및 통합 검증 조건을 대조해 미확정 사항과 원본과의 충돌을 도출한다. 조회 실패를 정보 부재나 영향 없음으로 판단하지 않는다.

사용자 결정이 필요한 항목은 근거, 실현 가능한 선택지와 장단점, 권장안 및 그 이유를 제시하고 대화한다. 중요한 요구사항·계약·인증·DB 등은 사용자의 명시적 결정을 기다리며 권장안을 승인으로 취급하지 않는다. 이미 확인된 결정을 재질문하지 않고 출처와 적용 범위를 기록한다. 미결 사항은 표시하고 관련 착수 준비를 보류한다.

## 계약 변경과 Issue 반영

공식 계약 변경이 필요하면 workflow의 계약 변경 Issue 절차에 따라 관련 기존 Issue를 확인해 재사용하거나 생성하고 필요성·근거·기준 원본·관련 Issue를 기록하며 설정된 Project에 등록·재조회한다. 이것은 변경안이나 계약 승인·명세 수정 권한이 아니다. 사용자에게 별도 `contract-management` 실행을 안내하고 자동 실행하지 않는다. 변경 계약에 의존하는 범위는 공식 원본에 반영되기 전까지 보류한다. 조회·권한 실패나 결과 불명 시 새로 생성하지 않고 재확인한다.

확인된 결정과 현재 공식 계약 URL·SHA를 Parent와 영향받는 Sub-issue에 필요한 범위로 반영한다. 기존 내용·후보 및 Link Key·관계·결정 이력·진행 상황을 보존하고, 기능별 책임·수용 조건·선행 조건·미결 항목을 명확히 한다. 서로 다른 계약 버전을 혼동하지 않는다. 사용자에게 정리 결과와 남은 조건을 제시하고 개발 착수에 대한 명시적 승인을 받는다. 승인과 필수 조건이 모두 충족될 때만 착수 가능하다고 보고하며, 해당 사용자 승인과 근거를 Issue에 기록한다. 필요한 경우 설정된 Parent 상태를 근거에 따라 조정하되 이후 자식 개발 상태는 담당 AI-DLC의 관리를 덮어쓰지 않는다. 승인하지 않았거나 원본·관계·필수 의존성이 미확인이면 착수 가능으로 표시하지 않는다.

실제 변경·재사용 Issue, 결정 출처, 원본 SHA, 미결 사항·승인 여부·재개 조건을 보고한다. 후보 발굴·Draft 전환·개발·계약 명세 수정이나 다른 Skill을 자동 실행하지 않는다.
