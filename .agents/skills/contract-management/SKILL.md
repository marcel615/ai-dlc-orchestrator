# 사용자 주도 공통 계약 관리

사용자가 자연어 또는 명시적 Skill 호출로 직접 요청한 경우에만 실행한다. 다른 Skill의 제안·연결이나 Issue 존재만으로 자동 실행하지 않는다. 공통 루트 `AGENTS.md`, `docs/workflow.md`, `docs/integration-checklist.md`, 대상 로컬 지시를 따른다. 자연어 변경 요청 또는 지정된 기존 Issue에서 시작하며 선행 Skill 실행은 필요하지 않다. 사용자가 분석만 요청하거나 범위를 제한하면 그 범위를 따른다.

## 원본·Issue와 영향 확인

요청의 목적·변경 범위와 관련 Issue·공식 관계·기존 결정을 확인하고, `requirements`와 관련 `contracts`의 설정된 역할·기본 브랜치 원본을 실제 조회해 URL·commit SHA를 기록한다. 기존 구현은 소비자 영향 근거이며 공식 원본 대체가 아니다. 명세 저장소 및 Project의 관련 열린·닫힌 Issue와 PR을 조회하고 workflow의 계약 변경 Issue 절차에 따라 기존 Issue를 재사용하거나 생성하고 Project에 등록·확인한다. 완료·종료된 과거 작업은 내용과 현재 반영 여부를 확인해 중복 여부를 판단하며 무조건 재사용하거나 재생성하지 않는다.

요구사항·API·인증·ERD·UI 간 일관성과 필요한 Backend·Frontend 소비자별 영향을 분석한다. 호환성, 기존 데이터·마이그레이션, 보안, 오류·경계 조건, 배포 순서·전환 기간·복구를 관련 범위에서 검토한다. 영향 없음에는 근거를 남기고 미연결·조회 실패는 보류로 구분한다. 관련 Parent·Sub-issue와 계약 변경 Issue를 상호 참조로 연결하되 기존 공식 Parent/Sub-issue 관계를 유지한다. 계약 Issue를 임의로 Sub-issue로 추가하거나 URL을 공식 관계로 주장하지 않는다. 각 관련 Issue에 영향·이유·재상세화 필요/불필요/판정 보류와 기준 SHA를 기록한다. 사용자 요청 범위 밖 수정은 하지 않는다.

## 협의·승인과 명세 PR

결정이 필요한 사항마다 근거·선택지·장단점·권장안을 제시해 사용자와 협의한다. 결정과 명시적 승인, 출처·범위·미결 사항을 계약 변경 Issue에 기록한다. 승인되지 않은 변경은 명세에 확정 반영하지 않는다. 계약의 의도된 변경에 대한 사용자 승인을 받은 뒤에만 관련 공식 명세를 수정하고, 실제 기본 브랜치의 최신 SHA와 승인·관련 Issue를 다시 확인한다. 기준이 바뀌어 승인 범위나 영향이 달라지면 재협의한다.

대상 Git 루트·원격·로컬 지시·작업 트리와 대상 PR 템플릿을 확인하고 기존 작업을 보존한다. 승인된 공식 원본만 작업 브랜치에서 수정하고 설정된 검증이 있으면 실행한다. 테스트 설정이 없거나 불명확하면 추측하지 않고 미검증을 보고한다. 공식 원본이 다른 저장소나 작업 트리에 있어 경로·원격·권한이 불명확하면 해당 부분을 보류한다. `orchestrator.default_branch`에 직접 Push하지 않는다. 변경 Issue와 승인 근거, 기준 SHA, 소비자 영향·미결 조건·검증 결과를 담은 PR을 대상 원본 저장소의 기본 브랜치로 생성한다. 권한이나 도구 제한으로 PR을 만들지 못하면 실제 완료 단계와 재개 조건을 보고한다. 사용자가 직접 Merge하며 자동 Merge하지 않는다.

PR은 제안이고 Merge 전 공식 계약이 아니다. Merge를 기다리거나 완료로 추정하지 않는다. 실제 Merge 이후에만 기본 브랜치 원본 SHA를 다시 확인해 관련 Issue의 기준과 재상세화 필요성을 기록한다. `issue-refinement`가 필요하면 사용자에게 별도 실행을 안내하고 자동 호출하지 않는다. 제품 구현, 통합 영향 검토의 상태 갱신, 개발 사이클은 실행하지 않는다. Issue·Project·PR 실제 상태, 승인·미결·영향·검증·Merge 여부와 재개 조건을 보고한다.
