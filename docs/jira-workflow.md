# Jira 작업 추적 절차

이 절차는 선택 서비스의 `work_tracking.provider: jira`에만 적용한다. 공통 `AGENTS.md`, 공식 원본 조회·사용자 결정·PR 분석·통합 완료 기준은 유지한다. GitHub는 코드·PR·리뷰·CI, 설정된 Specs 저장소는 공식 명세의 원본이다. GitHub Projects의 Draft·Approval·Sub-issue 또는 자동 Ready 전환 절차를 Jira에 적용하지 않는다.

## 설정과 실행 전 확인

선택 서비스의 `jira.site_url`, `project_key`, `issue_types.candidate/implementation/epic/contract`, `statuses.candidate/backlog/ready/in_progress/in_review/done`, 각 필요한 구현 역할의 `role_labels`, `approval`, `priority_order`를 읽는다. `approval`은 `user_transition_to_backlog`만 지원한다. 설정값은 실제 Jira 사이트·프로젝트·유형별 상태·우선순위 및 레이블 필드의 사용 가능 여부와 대조한다. 역할 레이블은 값과 작업 편집 권한을 확인하고 실제 작업에 설정한다. 기존 레이블 목록에 없다는 이유만으로 관리자에게 별도 사전 생성을 요구하지 않는다. 같은 상태의 중복 이름, 누락·잘못된 값, 조회·인증 실패, 필수 권한 또는 관계 지원 미확인은 해당 작업을 보류하고 보고한다. Jira 실패를 GitHub Projects로 대체하지 않는다.

연결된 Atlassian 도구를 우선 사용하고 목록은 마지막 페이지까지 확인한다. Jira 작업의 쓰기 전에는 해당 작업에 필요한 조회·생성·수정 권한과 필수 필드·상태 전환 조건을 확인한다. Epic이 필요한 경우에만 후보 유형 전환과 Task 상위 관계의 지원·권한·필드 및 상태 매핑을 확인한다. 상태나 유형이 존재한다는 사실은 전환 가능성의 증거가 아니다. GitHub Project 편집 권한·Draft·공식 Sub-issue 확인은 요구하지 않는다. 설정 변경이나 Jira 관리자 권한이 필요하면 보고하고 임의로 설정하지 않는다. 토큰 등 비밀을 기록하지 않는다.

## 후보와 승인

`feature-discovery`는 공식 원본과 GitHub의 구현·열린/닫힌 Issue·PR, Jira의 기존 후보·작업·관계를 조회하여 중복을 확인한다. 확인이 실패한 범위는 부재로 간주하지 않는다. 요청당 최대 3개의 유효 후보를 설정된 후보 유형으로 생성하고 `statuses.candidate`에 둔다. 각 본문에 고유 Candidate ID, 목적·예상 효과·차이·미결 사항과 제안 출처를 남긴다. 생성 시 기본 상태가 다르면 가능한 전환을 확인해 후보 상태로 이동하고 실제 상태를 조회한다. 후보 생성·상태 설정은 승인이나 개발 착수가 아니다.

사용자가 후보를 `statuses.backlog`로 직접 옮기는 것을 후보 승인으로 사용한다. 자동 정제 전 상태 이력에서 후보에서 백로그로의 전환자·시각을 확인하고 그 전환자가 사용자임을 신뢰할 수 있는 계정 정보와 대조한다. 채팅 등 별도 출처에 있는 승인도 작성자·대상·범위를 확인해 기록한다. 현재 상태만으로 승인자나 승인 범위를 추정하지 않는다. 이력·사용자 식별·승인 출처를 확인할 수 없으면 해당 후보는 보류한다. 승인 후 다시 후보 상태로 돌아갔다면 최신 전환과 승인 유효성을 다시 확인한다.

## 정제·연결

`cross-project-backlog-refinement`는 백로그 상태 작업을 끝까지 조회하고 Candidate ID, 제안 출처와 상태 이력으로 후보를 식별해 일반 구현·계약 Task와 구분한다. 후보 여부를 확인할 수 없는 작업은 보류한다. 사용자 승인 이력을 확인한 후보만 대상으로 최대 2개를 선정한다. 지정 후보를 우선하고 중복·목표·우선순위·의존성·공식 원본을 확인한다. 나머지는 실제 선행 관계와 `priority_order`를 따르고 동률은 생성 시각이 오래된 순, 다시 같으면 안정적인 이슈 ID 순으로 선정한다. 우선순위가 없으면 마지막에 두고 설정에서 해석할 수 없는 값이나 순환 의존성은 보류한다. 가능한 후보가 부족하면 채우지 않는다. 목표나 승인·의존성이 불명확하면 보류하고, 세부 결정이 남은 경우 질문과 함께 백로그에 둔다. 같은 요청의 부분 성공 재개도 최대 2개에 포함한다. 새 후보 등록이나 승인 변경은 수행하지 않는다.

후보의 키·목적·범위·제외·완료 조건·공식 원본 URL과 SHA·승인 이력을 보존한다. 독립 추적할 구현 작업의 수와 기능 전체의 완료를 함께 판단할 필요를 기준으로 아래 중 하나를 선택한다. Backend·Frontend 구분 자체는 Epic 생성 기준이 아니다. 실제 담당 저장소와 역할, 독립 실행 조건, 계약 참조·미결 조건을 본문에 기록한다. 정제와 상세화 단계는 별도 레이블을 만들지 않고 작업 종류와 본문의 체크리스트로 구분한다.

- 독립적으로 추적할 구현 작업이 하나면 기존 후보를 같은 키의 `issue_types.implementation` Task로 유지하고 해당 역할 라벨·구현 범위·완료 조건을 추가한다. 별도 구현 Task나 Epic을 만들지 않는다. 후보 유형이 구현 Task가 아니면 같은 키로 변경 가능한지 확인하고 불가능하면 보류한다.
- 여러 구현 작업을 따로 추적하고 기능 전체의 완료를 함께 판단해야 하면 기존 후보를 같은 키의 `issue_types.epic`으로 전환한다. 그 아래 필요한 구현 Task만 생성하거나 기존 Task를 재사용하고 역할 라벨을 붙인다. 기존 후보를 자식으로 남기거나 별도의 대체 Epic을 만들지 않는다. 여러 작업이지만 통합 완료 판단이 필요한지 불명확하면 구조를 추정하지 않고 보류한다.

후보 본문의 정제 체크리스트에 필요한 역할·작업·관계별 결과를 기록한다. 정제 완료 후보는 자동 선정에서 제외하고, 부분 성공 후보는 실제 작업·관계를 재조회한 뒤 남은 단계부터 재개한다. 기존 후보의 완료 여부가 불명확하면 임의로 새 작업을 만들지 않고 확인한다. 사용자 후보에 Candidate ID가 없으면 기존 Jira 이슈 키를 안정 식별자로 사용한다.

Epic 전환 전 같은 프로젝트·같은 키 유지, 현재 상태와 대상 상태, 필수 필드, 기존 본문·승인 이력·첨부·관계 보존 및 전환 권한을 확인한다. 도구가 미리보기나 별도 확인을 요구하면 그 절차를 따르고, 지원 여부·보존·결과가 불명확하거나 전환이 실패하면 별도 Epic으로 우회하지 않고 보류한다. 전환 후 원래 키·유형·상태·보존 항목을 재조회한다. 필요한 Task를 Epic의 자식으로 연결한 뒤 각 자식의 상위 항목과 Epic의 자식 목록을 양쪽에서 재조회한다. 다른 상위 항목이나 기존 관계를 임의로 교체하지 않는다.

구현 Task는 `statuses.backlog`에 둔다. 생성 기본 상태가 다르면 전환 가능 여부를 확인해 백로그로 이동하고 결과를 확인한다. `statuses.ready`로 이동하지 않는다. 자식 생성 전후 Candidate ID와 `Link Key: <후보 URL>|<대상 저장소>|<작업 식별자>`로 기존 작업을 확인하고 중복을 피한다. 쓰기·유형 전환 결과가 불명확하면 원래 키의 실제 유형·작업·관계를 재조회하고 이미 성공한 단계를 반복하지 않는다. 관계 조회 실패는 미연결이 아니다.

## 상세화·계약·착수

`issue-refinement`는 지정된 Jira 작업과 검증된 관련 관계·결정·의존성·GitHub PR 및 공식 원본 URL·SHA를 확인한다. 구현 Task의 범위·완료 조건·오류·의존성·결정 출처와 미결 사항을 본문에 정리하고 기존 이력과 관계를 보존한다. 필요한 계약 변경 작업은 `issue_types.contract`로 기존 Jira 작업을 확인해 재사용하거나 생성하고 관련 작업과 상호 참조한다. 관련 참조를 Epic 상위 관계로 오인하지 않는다. 계약 변경 작업 등록은 명세 변경 승인이 아니다.

상세화 결과와 미결 조건을 사용자에게 보고한다. 후보 승인은 착수 승인이 아니다. 필수 조건과 사용자의 결정이 갖춰져도 Orchestrator는 구현 Task를 `statuses.ready`로 옮기지 않는다. 사용자가 실제 착수할 Task를 직접 옮긴다. 이미 진행 중인 상태를 덮어쓰지 않는다. 다른 Skill이나 개발은 자동으로 시작하지 않는다.

`contract-management`는 사용자의 직접 요청에서 독립 실행하고 Jira 계약 작업에 결정·영향·공식 원본을 기록한다. 승인된 변경만 공식 Specs 저장소의 PR로 제안하고 실제 Merge 전까지 공식 원본으로 취급하지 않는다. `integration-review`는 Jira 작업·관계를 조회해 재사용이나 후속 작업을 제안하되 검토 요청만으로 생성·상태 변경하지 않는다.

## 자동화와 완료 확인

구현 PR이 검토 가능한 상태일 때 `statuses.in_review`, 지정된 개발 대상 브랜치에 실제 Merge됐을 때 `statuses.done`으로 옮기는 자동화는 Jira Automation의 설정과 동작을 별도 확인한다. PR 생성이나 Merge를 자동화 성공으로 간주하지 않고 실제 상태를 조회한다. 브랜치·PR 연결·작업 유형별 적용 범위를 검증하지 못하면 미검증으로 보고한다. 개별 구현 Task의 완료는 공통 기능의 통합 완료가 아니다. 공통 기능은 필요한 구현·계약·통합 검증을 확인한 뒤 완료를 판단하고 자동화가 공통 기능을 조기 완료하지 않는지 확인한다.
