# 통합 조정 절차

## 실행 경계와 설정 해석

먼저 `AGENTS.md`와 `ai-dlc.yaml`을 확인한다. 아이디어 제안 요청은 최대 3개 Pending Draft 등록, 백로그 정제 요청은 Approved 후보 최대 2개의 Parent 전환·필요 Sub-issue 생성·공식 연결·Project 초기 반영까지 포함한다. 정상 범위의 실행 승인을 반복 요청하지 않는다. 변경 영향 검토 요청은 분석·후속 작업 제안과 로컬 상태 갱신을 수행하며 실제 후속 Issue·Draft 등록을 자동 실행하지 않는다. 사용자의 분석 전용·등록 제외·대상 제한 지시를 우선한다.

통합 저장소 자체의 문서·브랜치·커밋·Push·PR 유지보수는 사용자에게 요청받은 범위에서 수행한다. 후보 승인·중요한 정책·요구사항·계약·인증·DB 결정은 사용자에게 확인하고 미결정 범위를 임의 확정하지 않는다. `ai-dlc.yaml`의 `orchestrator.default_branch`에 직접 Push하지 않으며 자동 Merge는 하지 않는다. 서비스 제품 구현은 각 AI-DLC에 맡긴다.

schema version 2에서 사용자 지정 서비스 키를 우선하고 없으면 `active_service`를 사용한다. 선택한 `services` 항목의 `repositories`, `backlog`, `project`, `labels`, `requirements`, `contracts`를 해석한다. 지원하지 않는 버전, 없는 서비스·역할, 잘못된 연결은 보류하며 다른 서비스나 통합 저장소로 대체하지 않는다.

`backlog.parent_repository_role`이 Parent 저장소, `backlog.implementation_repository_roles`가 구현 대상이다. 비활성 역할이 실제로 필요하면 그 부분의 계획·생성을 보류한다. 필요하지 않은 역할에 작업을 만들지 않으며, 비활성 상태 자체를 기능 대상외의 근거로 삼지 않는다.

| 정보 | 원본 |
|---|---|
| 비전·후보·사용자 승인 | 설정된 Project README·Draft·Approval |
| 공식 공통 요구사항 | `requirements`의 저장소 역할·경로·기본 브랜치와 조회한 SHA |
| 기능별 목적·범위·완료 조건·결정 이력 | 공식 요구사항을 참조하는 공통 관리 저장소의 Parent Issue |
| 구현·개발 상태 | 필요한 구현 저장소의 Issue·PR·CI |
| API·인증·ERD·UI | `contracts`의 계약별 저장소 역할·경로·기본 브랜치와 조회한 SHA |
| 표시 상태 | Project. 원본과 모순되면 확인 필요 |
| 중요한 결정 | 사용자 대화·코멘트의 작성자와 출처 |

`contracts.ui`는 화면 구성·라우팅·사용자 동작·로딩/빈 결과/오류·입력 검증/중복 제출 등 공통 UI 처리의 공식 기준이다. API·인증·데이터 구조는 각 공식 명세를 따르고, UI 내부 구현 설계·개발 진행 상태는 Frontend Issue·PR에서 확인한다. 기존 구현 저장소의 UI 문서나 코드로 공식 UI 명세를 대체하지 않는다. 공식 명세 간 충돌·미결정 사항은 Parent에 근거와 결정 질문을 남기며 임의로 확정하지 않는다.

`requirements`와 `contracts`의 `repository_role`을 선택 서비스의 `repositories`에 연결하고, 해당 역할의 `default_branch`에서 `path`를 조회한다. 실행 시 브랜치의 commit SHA를 먼저 확인하고 그 SHA로 문서를 읽어 원본 URL·commit SHA·경로를 기록한다. 같은 저장소의 원본은 같은 조회 기준 SHA를 사용하고 다른 저장소에는 각자의 SHA를 사용한다. `reference_commit`은 원본 저장소에서 확인한 조사 출발점이며 현재 버전을 고정하지 않는다.

공식 요구사항·API·인증·ERD·UI의 기준은 설정된 원본이다. 구현 저장소에 남아 있는 명세 사본은 구현 비교·과거 이력에만 사용하며 공식 원본으로 취급하지 않는다. 원본 조회 실패 시 구현 저장소의 사본이나 Parent 본문으로 대체하지 않고 필요한 작업을 보류한다. 원본·Parent·구현 간 불일치는 근거와 사용자 결정 필요 사항을 보고하며 어느 쪽도 임의로 덮어쓰지 않는다.

`templates/docs/`의 요구사항·API·ERD·UI 문서는 초기 작성 양식이다. 대상 프로젝트의 명세로 작성·검토·승인하기 전에는 공식 원본으로 간주하지 않으며, 기존 공식 명세 파일을 덮어쓰지 않는다.

연결된 도구를 우선한다. Draft·Project·공식 관계 기능이 부족하면 허용된 기존 인증의 CLI/API를 사용한다. 기기별 실행 경로·인증 정보를 공통 정책에 고정하지 않는다. 목록은 마지막 페이지까지 확인하고 검색 결과만으로 부재를 확정하지 않는다.

쓰기 전에는 대상 저장소의 Issues 활성화·Issue와 라벨 변경 권한, 공식 Sub-issue 추가·조회 지원과 소유자 조건, Project 편집 권한·필드·선택지를 각각 확인한다. 저장소 접근 성공이나 Project 조회 성공은 외부 쓰기 성공의 증거가 아니다. 부족한 권한이나 관계 지원을 URL 링크로 우회하지 않는다.

## 공통 Draft 제안·정제

제안은 `backlog.draft_skill`의 `feature-discovery`, 승인 후보 정제는 `backlog.refinement_skill`의 `cross-project-backlog-refinement`가 담당한다. `integration-review`는 PR·계약 변경 영향을 분석한다. 각 Skill은 사용자 지시로 독립 실행하고 필요한 실제 원본을 직접 조회한다. 선행 Skill 실행을 요구하거나 다음 Skill·개발 사이클을 자동 시작하지 않는다. 개별 AI-DLC에는 Draft 작업을 별도 요청하지 않으며 기존 기능을 수정하지 않는다. 개발 중 발견한 필수 기술 후속 작업은 해당 저장소의 기존 절차와 중복 검사로 조정한다.

### 제안

`feature-discovery`는 사용자가 요청한 기능 아이디어를 프로젝트 전체 사용자 흐름과 Project 비전·공통 요구사항·계약·각 구현 저장소·열린/닫힌 Issue·PR·기존 Draft와 비교한다. 유효 후보만 최대 3개 선정하며 필요성·차이·예상 효과·미결정 사항을 정리한다. 수를 채우기 위해 후보를 만들지 않는다. 필수 자료가 없으면 중복 확인 범위와 보류 사항을 명시하고 확인 전 등록하지 않는다.

`아이디어 제안해`는 설정된 Project에 유효 후보 최대 3개를 Pending Draft로 등록한다. 대상·권한·중복을 확인한 뒤 등록하며 후보마다 추가 승인을 요구하지 않는다. 사용자가 등록을 제외하면 본문·필드안만 보고한다. 이 요청은 후보 승인·백로그 정제·개발 시작 권한을 포함하지 않는다.

고유 Candidate ID와 식별 정보를 본문에 포함하고 설정된 AI 제안자·Pending 매핑을 사용한다. 개발 Status는 비운다. 비전·후보 승인은 사용자만 변경한다. 재개 시 이미 등록한 후보도 같은 요청의 최대 3개에 포함한다. 등록·필드 설정 결과가 불명확하면 식별자로 재조회하고 중복 여부 확인 전 재등록하지 않는다. 결과 보고 뒤 종료하며 승인·정제·개발을 자동 시작하지 않는다.

### 정제 후보 자동 선정

`백로그 정제해`에서 후보를 지정하지 않으면 설정된 Project의 Draft 전체를 페이지 끝까지 조회하고 실제 Approved 매핑인 후보를 자동 탐색한다. 사용자가 지정하면 지정 순서를 우선하되 승인·중복·목표·의존성 확인은 생략하지 않는다. 명시적으로 특정 후보만 요청했다면 범위 밖을 추가하지 않는다. 한 요청은 지정·자동 후보와 부분 성공 재개를 합쳐 최대 2개이며, 유효 후보가 부족하면 수를 채우지 않는다.

- 이미 정식 Issue로 전환되었거나 같은 기능이 존재하면 새 Parent를 만들지 않고 기존 작업·이력을 보고한다. 진행 중 부분 작업의 재개는 신규 후보 선정과 구분한다.
- 목표 자체가 불명확한 후보, 승인 확인 실패·우선순위 충돌·의존성 판단 불가·순환은 자동 선정에서 보류하고 이유를 보고한다. 상세 결정만 미정이면 질문·결정 라벨·Backlog로 정제할 수 있지만 착수 준비 완료로 취급하지 않는다.
- 후보의 우선순위는 Draft의 Project Priority를 설정 매핑으로 해석한다. 실제 Issue가 연결된 경우 라벨과의 충돌을 확인한다. 순서는 high→medium→low→미설정, 동률은 생성 시각이 오래된 순→안정적인 후보 ID 순이다. 필요한 값이 없거나 해석할 수 없으면 임의 추정하지 않는다.
- 실제 Issue의 Blocked by와 명시된 선행 조건을 확인한다. 후보 간 선행 관계가 확인되면 그 선행 후보를 먼저 정제한다. 선행 구현이 미완료여도 범위가 명확하면 정제는 가능하나 Backlog와 의존 관계를 유지한다. 정제를 개발 착수와 혼동하지 않는다.
- 지정 후보를 먼저 검토하고 남는 자리는 위 기준으로 선정한다. 지정 후보가 미승인·보류라면 그 사실을 보고한다. 선정·제외·보류·기존 작업 재사용의 근거와 조회 범위를 남긴다.

### 정제

1. `cross-project-backlog-refinement`는 위 절차로 최대 2개를 선정하고 승인 출처·현재 Approved 매핑·전환 이력을 확인한다. 사용자나 다른 경로로 등록된 후보도 실제 승인을 확인해 처리할 수 있으며 `feature-discovery` 실행을 요구하지 않는다. 신규 아이디어 발굴·Draft 등록·승인 변경은 수행하지 않는다. 승인되지 않은 후보는 정식 Issue화하지 않는다. 목표가 불명확하면 Draft로 유지하고, 세부 결정만 남으면 결정 질문·설정된 결정 라벨과 Backlog 상태를 제안한다.

2. 공식 요구사항·API·인증·ERD·UI와 공통 관리 저장소·구현 저장소의 열린·닫힌 Issue·PR·후보를 확인한다. 기존 Parent·구현 작업을 재사용하고 필요한 구현 범위만 나눈다. Parent와 구현안은 관련 공식 원본의 URL·SHA를 참조하고 기능별 범위·완료 조건을 작성한다. 각 구현안은 해당 저장소 템플릿과 독립 실행 요건을 따른다. 원본의 세부 명세를 복제하거나 정제만으로 변경을 승인하지 않는다.

3. Parent·구현 본문, 대상 역할, 식별자, 공식 관계, 우선순위·실제 선행 관계·미결정 사항을 정리한다. 분석·계획만 요청한 경우 여기서 보고하고 종료한다. 그 외에는 아래 생성·연결까지 수행한다. 개발은 시작하지 않는다.

4. 변경 직전 후보 승인·중복을 재확인하고, 기존 Parent가 없으면 Draft를 설정된 Parent 저장소의 Issue로 전환하는 방식을 우선한다. 원래 Draft를 남긴 채 별도 Parent를 추가 생성하지 않는다. 기존에 정식화된 후보는 임의 이동·복제하지 않고 이력을 보존해 공통 Parent 필요성을 판단한다.

5. 필요한 구현 Issue만 생성하거나 기존 Issue를 재사용하고 공식 Sub-issue 관계를 등록한다. BE만 또는 FE만 필요하면 해당 역할만 처리한다.

6. Parent와 Sub-issue의 Project 등록·필드·공식 관계 결과를 재조회한다. 후보 승인·Candidate ID·연결 이력을 보존한다. 부분 성공이면 성공한 대상과 재개 지점을 보고하고 무조건 재실행하지 않는다.

## 식별자·공식 관계·부분 실패

후보 식별자는 `Project ID + Candidate ID`이며 기존 ID를 보존한다. ID가 없는 기존 Draft는 node ID를 사용한다. Parent에는 원본 후보·Project·ID를 남긴다. 구현 작업의 안정 식별자는 `Link Key: <Parent URL>|<대상 owner/repo>|<작업 식별자>`다. 같은 작업 재개 중 식별자를 바꾸지 않는다. 키가 없는 기존 작업도 목적·범위가 같으면 재사용한다.

필수 연계 작업이 공통 기능에 속하면 기존 Parent 아래에 연결한다. 특정 PR의 독립 기술 후속 작업은 원본 PR URL을 식별 기준으로 사용할 수 있으며, 단순 후속 작업마다 공통 Parent를 강제로 만들지 않는다.

공식 관계의 식별 기준은 Parent와 Sub-issue의 실제 Issue ID다. API의 Issue ID·node ID·저장소 내 번호를 혼동하지 않는다. 생성과 관계 추가는 별도 작업으로 확인한다.

| 현재 상태 | 처리 |
|---|---|
| 같은 작업 Issue 존재 | 생성 생략, 기존 작업 재사용 |
| 같은 Parent 관계 존재 | 관계 추가 생략, Project 등 남은 단계만 확인 |
| Parent 미지정 | 승인된 범위에서 공식 관계 추가 후 재조회 |
| 다른 Parent에 연결됨 | 자동 교체하지 않고 충돌 보고·사용자 판단 대기 |
| Issue 생성 후 관계 추가 실패 | 기존 Issue를 식별해 연결 단계부터 재개 |
| 관계 추가 후 Project 반영 실패 | Issue·관계 재생성 없이 Project 단계부터 재개 |
| Draft 전환 결과·생성 결과 불명 | 후보 식별자·전환 결과·Issue를 재조회, 확인 전 재생성 금지 |
| 관계 조회 실패 | 미연결로 추정하지 않고 해당 작업 보류 |

공식 관계 등록 후 Parent의 Sub-issue 목록과 자식의 Parent를 조회해 양쪽 ID를 확인한다. 본문 URL·체크리스트·관련 링크는 보조 근거일 뿐 관계 완료가 아니다. 다른 Parent를 가진 기존 작업은 참고 링크로 남길 수 있지만 이번 Parent의 Sub-issue로 연결되었다고 보고하지 않는다. 해당 작업의 완료 증거는 별도로 평가한다.

통합 조정은 Main의 단일 실행으로 수행한다. 검색으로 동시 생성을 원자적으로 막을 수 없으므로 경쟁 실행 시 쓰기를 보류한다. BE/FE의 독립 개발은 계속 가능하다.

## 계약과 변경 영향

### 요청 시 PR 탐색과 이력

특정 PR을 지정하면 그 PR을 우선 확인한다. `변경 영향 검토해`처럼 지정이 없으면 선택 서비스의 활성·연결 확인된 저장소 역할 전체에서 신규·갱신 PR을 탐색한다. 공통 관리 저장소도 포함하고 같은 저장소는 한 번만 조회한다. 비활성·미연결 저장소는 누락 범위를 보고한다. 별도 상시 감시·서버·주기 작업은 만들지 않는다.

검토 재사용에는 `review.state_file`의 단일 JSON 상태를 사용한다. 검증 보고서를 생성·검색하지 않는다. 같은 파일의 서비스별 저장소·PR 최신 상태만 갱신하며 매 실행 이력을 누적하지 않는다. 파일이 없으면 빈 상태로 시작하고, 손상되었거나 읽지 못하면 완료로 추정하거나 임의 덮어쓰지 않고 그 한계를 보고한다.

1. 요청 시작 UTC를 이번 조회 상한으로 고정한다. 저장소별 마지막으로 확인한 완료 기준 시점을 하한으로 사용하고 경계 시각은 포함해 조회한다. 이력이 없는 첫 조회는 사용자가 기준 시점을 지정하지 않는 한 전체 PR 이력을 대상으로 한다. 사용자 지정 범위가 더 좁으면 그 범위만 검토한 것으로 기록한다.

2. open뿐 아니라 closed·merged를 포함한 PR 목록의 생성·갱신 시점과 최신 head/base를 페이지별로 조회한다. 요청 상한 이후 갱신은 다음 조회 대상으로 남긴다. 같은 PR은 저장소·번호로 합치며 조회 중 변동·누락이 의심되면 구간을 재확인한다.

3. 같은 PR URL·base SHA·head SHA·PR 상태와 관련 공식 요구사항·계약 원본의 저장소·경로·SHA·소비자 기준 SHA·PR 본문·관련 코멘트와 사용자 결정 출처 버전이 모두 같고 이전 분석이 완료된 경우만 상세 분석을 재사용한다. updatedAt은 탐색 단서이며 단독 완료 키가 아니다. 원본의 위치·요구사항·계약·소비자·결정 맥락이 바뀌면 갱신 PR뿐 아니라 영향을 받는 기존 검토 대상도 재평가한다. 이전 분석이 비공식 명세 사본을 기준으로 했다면 설정된 공식 원본을 기준으로 재검토한다.

4. 이전 보류·실패 건은 최신 PR 목록에 다시 나타나지 않아도 재개 대상으로 확인한다. 실제 diff로 영향 없음·호환 영향·비호환 영향·보류를 분류하고 영향 없는 변경도 이유·분석 버전을 기록한다. 검토 맥락이 그대로인 완료 건은 재분석하지 않고 재사용 사실만 보고한다.

5. 상태 파일의 해당 서비스·저장소·PR 항목을 최신 값으로 교체하고 다른 항목은 보존한다. 목록·필수 분석이 끝난 저장소만 완료 기준 시점을 전진시키고 실패·보류 건은 재개 대상으로 유지한다. 상세 결과·근거·누락 범위는 최종 응답이나 승인된 PR 본문에 보고한다. 상태를 저장하지 못하면 중복 생략을 보장하지 말고 한계를 보고한다.

상태 파일은 `schema_version: 1`, `services` 객체를 가진다. `services[서비스 키]` 아래에 다음 최신 값만 둔다. 빈 초기 상태는 실제 스캔·분석 완료를 뜻하지 않는다.

| 위치 | 저장할 최소 상태 |
|---|---|
| `repositories[owner/repo].completed_through` | 전체 조회·필수 분석이 끝난 UTC 상한. 미완료이면 이전 값 유지 또는 null |
| `pull_requests[PR URL]` | base_sha, head_sha, pr_state, source_updated_at, context, analysis_status, verdict, reviewed_at |
| PR의 `context` | 관련 공식 요구사항·계약의 저장소·경로·SHA, 소비자 SHA, PR 본문·관련 코멘트·사용자 결정의 버전 참조 또는 해시. 원문·비밀값은 저장하지 않음 |
| PR의 `analysis_status` | complete 또는 deferred. 실패·필수 정보 부족은 deferred로 남겨 재조회 |

관련 UI 명세도 `context`의 계약 원본에 포함한다. UI 원본 추가·변경으로 영향 범위가 달라지거나 이전 분석에 관련 UI 기준이 빠져 있으면 해당 분석을 재검토한다.

단일 PR 검토는 해당 PR 항목만 갱신하고 저장소 전체 완료 시점을 전진시키지 않는다. 변경·보류 PR은 최신 상태로 재검토하며 같은 맥락의 complete만 재사용한다. 상태 쓰기는 파일 전체를 검증해 교체하고 실패하면 이전 파일을 보존한다. 보고서·날짜별 상태 사본·별도 DB·실행 서버는 추가하지 않는다. 저장소 완료 시점은 PR 탐색 범위이며 기능 통합·배포 완료가 아니다.

### 변경 분석

공식 요구사항은 `requirements`, API·인증·ERD·UI는 `contracts`에서 해석하고 위 원본 조회 절차를 적용한다. 현재 원본 SHA와 대상 PR base/head는 별도로 확인한다. 명세 저장소 PR은 해당 문서의 base/head를 비교하고, 구현 저장소 PR은 실제 구현 diff를 현재 공식 원본과 대조한다. 구현 저장소에 남아 있는 명세 사본의 변경만으로 공식 계약이 변경된 것으로 판단하지 않는다. OpenAPI가 설정되어 있지 않으면 존재를 가정하거나 사본을 만들지 않는다.

Parent는 공식 요구사항·API·인증·ERD·UI의 관련 URL·SHA를 참조해 기능별 범위·완료 조건·결정 이력을 관리한다. 원본 관리 역할은 사용자 승인에 따라 명세를 반영하고, 각 구현 AI-DLC는 구현 일치성과 소비자 영향을 확인한다. 통합 AI-DLC는 변경 제안·원본 버전·연계 작업·검증 증거를 조율한다. 중요한 요구사항·계약·인증·DB·비호환 전환·최종 Merge는 사용자 결정이다. 통합 조정 저장소의 설정 변경만으로 연결 저장소의 문서·개발 절차가 수정되는 것은 아니다. 연결 저장소에 정리되지 않은 참조가 남아 있으면 필요한 후속 작업안으로 보고한다.

구현 저장소뿐 아니라 공통 요구사항·API·인증·ERD·UI 변경 PR도 영향 분석 대상이다. 대상 PR base/head SHA와 전체 변경 파일에서 시작하고 요구사항·계약·ERD·UI·화면·라우팅·엔티티·마이그레이션·DTO·컨트롤러·인증·관련 테스트 diff를 확인한다. patch 누락·잘림은 원문으로 보완한다. 본문이나 파일 이름만으로 판정하지 않는다.

| 판정 | 처리 |
|---|---|
| 영향 없음 | 계약·관측 동작 유지 근거를 남기고 추가 작업 미생성 |
| 호환 영향 | 기존 사용 유지 여부와 소비자 대응 필요성을 확인 |
| 비호환 영향 | 사용자 결정·소비자 대응·호환 기간·배포 순서·복구 제약 제시 |
| 판정 보류 | 원본 불일치·소비자 미연결 등 부족한 근거와 재개 조건 제시 |

`integration-review`는 선행 후보·정제 기록 없이도 지정 PR과 계약의 실제 원본으로 실행할 수 있다. 서버 차이·소비자 사용·Issue 필요성을 별도로 판단한다. 새 API 추가와 기존 요청의 인증 조건 변경은 분리한다. 미연결 소비자는 영향 없음이 아니다. 필수 연계 작업은 Issue안, 선택 기능은 별도 기능 검토가 필요한 사항으로 보고하되 Draft 등록·후보 승인·정제를 수행하거나 다른 Skill을 자동 호출하지 않는다. Merge된 PR의 사후 검토는 Merge 전 게이트 실증이 아니며 수동 검토로 Merge 차단을 보장하지 않는다.

## 상태·완료·재개

Draft 개발 상태는 비우고 승인 값은 사용자만 변경한다. 정식 Issue의 상태는 설정된 매핑을 사용한다. 미결정·선행 조건이 남으면 Backlog, 준비되면 Ready다. 부모는 조정 시작 후 In Progress, 필요한 구현이 갖춰지고 통합 검증 대기면 In Review, 완료 조건 충족 후 Done이다.

백로그 정제 요청의 생성 작업에서 통합 AI-DLC는 Parent·Sub-issue 최초 Project 등록과 확인된 초기 상태·라벨을 설정한다. 이후 자식의 개발 상태는 담당 AI-DLC가 관리하며 통합 AI-DLC가 덮어쓰지 않는다. Parent 상태는 통합 AI-DLC가 근거로 판단한다. 우선순위는 Issue 라벨과 Project 매핑을 대조하고, 기한은 사용자 지정만 사용한다. 실제 선행 조건에만 Blocked by를 사용한다.

Parent 완료는 필요한 구현·계약 반영·통합 검증 증거를 모두 확인한 상태다. Sub-issues progress 100%나 단순 close로 완료하지 않는다. 개별 PR이 공통 Parent를 자동 종료하지 않도록 종료 참조·Project 자동화의 영향을 확인한다. 영향 검토에서는 불일치를 보고하고 필요한 수정안을 제안하며 검토 요청만으로 상태를 변경하지 않는다.

배포 필요 여부와 검증 환경은 Parent 완료 조건에서 정한다. 필요한 배포·검증이 미확인이면 보류하고, 모든 작업에 운영 배포를 일률적으로 요구하지 않는다. 제품 테스트 구현·실행은 각 AI-DLC 또는 사용자가 맡고 기존 CI·E2E 증거를 재사용한다.

생성·연결 작업에서는 Parent 본문·체크포인트에 후보/Link Key, 승인 출처, 단계별 성공 여부, Issue·관계·Project 식별자, PR head·계약 SHA와 남은 작업을 남긴다. 일반 검증 결과는 최종 응답이나 승인된 PR 본문에 보고하고 Markdown 보고서를 별도로 만들지 않는다. PR 분석의 재사용 상태만 단일 JSON에 갱신한다. 재개 시 실제 상태를 재조회하고 head·계약 변경에 관련 판정·검증을 갱신한다. 단순 close·not planned·Merge·배포를 구분하며 별도 DB는 만들지 않는다.
